# クロールの待機・減速と再開位置

全サイト共通で、同一サイトの Scrapy リクエストを直列化する。既存の
`CrawlingDomainDuplicatePrevention` による多重起動防止は継続する。
HTTP と HTTPS、同じスパイダーのサブドメインへの送信も同じ待機状態を使う。

## 送信間隔

- 基準間隔は初期値3秒。429を受けるたびに3秒加算し、最大60秒とする。
- 429では60秒待機して同じURLを再試行する。`Retry-After` がそれより長ければその期限まで待つ。
- 429の減速状態を保存した後、既存の `slack_notice` で通常チャンネル
  (`BROWNIE_ATELIER_NOTICE__SLACK_CHANNEL_ID__NOMAL`) に通知する。
  サイト・スパイダー・変更前後の基準間隔・待機時間・再開可能日時（UTC）を送る。
  429ごとに通知し、間隔の上限到達後も通知する。503や通常のAutoThrottle調整では通知しない。
  Slack通信は別スレッドで行い、通知例外でクロールを停止しない。通常終了時は通知完了を待つ。
- 503に有効な `Retry-After` がある場合も待機・再試行するが、基準間隔は加算しない。
- 403は再試行しない。ヘッダーなし503や通信エラーには既存の有限リトライを使う。
- AutoThrottle は応答時間によって基準間隔以上に減速する。基準間隔はその実行中に引き下げない。
- AutoThrottle の一時的な調整値は保存しない。調整ログは `SCRAPY__LOG_LEVEL=DEBUG` の場合のみ出力する。

controller の保存例（日時は UTC の BSON Date）:

```text
domain: yomiuri_co_jp
document_type: download_control
download_delay: 6
retry_after_until: <送信を再開してよい日時>
```

この状態は警告を受けた時点で保存し、次回起動時に読み込む。`crawl_point_non_update` は従来どおり
クロールポイントだけのテスト用フラグで、サイト保護のための減速状態の保存は止めない。
取得地点の更新は domain と document_type の両方を条件にし、上記レコードを上書きしない。

`settings.py` の主な調整項目:

| 設定 | 初期値 | 用途 |
|---|---:|---|
| DOWNLOAD_DELAY | 3 | 保存値がないサイトの基準間隔（秒） |
| RATE_LIMIT_DELAY_STEP | 3 | 429のたびに加える秒数 |
| RATE_LIMIT_MAX_DELAY | 60 | 429による基準間隔の上限 |
| RATE_LIMIT_COOLDOWN | 60 | 警告時の最低待機秒数 |
| RATE_LIMIT_MAX_RETRIES | 5 | 待機を伴う1リクエストの再試行上限 |
| RATE_LIMIT_MAX_WAIT | 900 | 1クロールの警告による待機時間の合計上限（秒） |
| AUTOTHROTTLE_MAX_DELAY | 60 | 応答時間による追加減速の上限 |
| CONTINUED_MAX_LISTING_PAGES | 100 | URL方式の前回地点を探す一覧ページ数上限 |

上限を超えた場合は追加送信を停止する。長い `Retry-After` を上限に切り詰めて早く再送することはしない。
保存済みの基準間隔が設定上限より長い場合も、起動時に勝手に短縮しない。

## controller の再開位置

### draw.io による機能別フロー

[次回クロールポイントの解説図（crawl_checkpoint.drawio）](crawl_checkpoint.drawio) は、
draw.io / diagrams.net で編集できる図です。開いた後、下部のページタブを順に切り替えてください。
単一ファイルの処理順ではなく、スパイダー・共通処理・ミドルウェア・controller をまたぐ役割を図示しています。

| ページ | 解説内容 |
|---|---|
| 1 全体像 | 前回位置の取得、今回の進捗記録、終了時の判定、controller 更新 |
| 2 記録と共通判定 | 要求・解析・保存の違い、記事発見の完了確認、分割記事を含む未完了判定 |
| 3 lastmod 方式 | 同時刻の記事をまとめて扱い、最も古い失敗時刻より前まで進める具体例 |
| 4 URL 方式 | 未完了記事より古い側から再開の目印を選ぶ具体例と、目印不足時の扱い |

青は処理、橙は判定、緑は採用する結果、赤は前回位置の維持または更新なし、黄は補足説明です。
「前回位置を維持」は更新処理自体の省略ではなく、前回と同じ位置を保存する意味です。
テスト用の `crawl_point_non_update` が有効な場合のみ、クロールポイントの更新を省略します。
図中の関数名から実装を追えます。待機・減速制御は別機能のため、この図には含めていません。

### 判定の要点

HTTP成功だけでなく、記事の MongoDB 保存成功を確認してから完了と判定する。
記事の2ページ目以降が未完了の場合も、その記事全体を未完了として扱う。

- sitemap方式: 同じ lastmod の対象記事がすべて保存できた時刻のうち、最も古い失敗時刻より前まで進める。
  10:00成功・10:05失敗・10:10成功なら、10:00を保存し、次回10:10の再取得を許容する。
- URL方式: 新しい順の一覧で最も古い未完了記事より後ろの10件を目印にする。
  順序はページ番号から復元し、再試行による応答順の逆転に左右されない。
  安全な10件が足りない場合は前回の目印を維持する。
- サイトマップ・一覧自体が未取得/解析失敗の場合は、未発見の記事の時刻や位置が不明なので前回位置を維持する。
  毎日の一覧も前回の目印まで追加読み込みする。探索上限に到達した場合は前回位置を維持する。

対象は Scrapy が管理するリクエスト（Playwright経由のページ取得を含む）。ブラウザー内部の広告・画像・
JavaScriptによる追加通信は Scrapy のリクエストキューを通らないため、この送信間隔の制御対象外。
再開位置は取得した一覧の並び順に基づくため、サイト側で記事の並びが変更された場合まで完全には保証できない。

## 検証

```bash
PYTHONPATH=app .venv/bin/python -m unittest discover -s tests -p 'test_crawl_control.py' -v
```

実サイトとMongoDBには接続せず、Scrapy 2.18のキューを模擬ハンドラーで動かす。
429の待機中にキュー済みの要求が送信されないこと、別クローラーが動き続けること、
上限での停止、保存状態の復元、部分完了・リダイレクト・ページ分割・保存失敗を検証する。
`ThrottledDownloader` は Scrapy の `_download` と AutoThrottle の拡張点を使うため、
Scrapy更新時にはこのテストを再実行する。
